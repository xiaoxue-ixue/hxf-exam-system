## 第 0 轮　开测前准备

### 0-1　确认服务在跑

```bash
# 后端探活，应返回 code=200
curl http://localhost:8080/hello
```

或者浏览器直接打开 `http://localhost:8080/hello`，看到 `hello,在线考试系统后端启动成功！` 即可。

### 0-2　跑自检脚本，抄下基线

```bash
node exam-backend01/scripts/verify-api.mjs
```

脚本会打印当前所有用户和 id。**把这一段抄下来**，它是后面所有 id 判断的基准：

```
id=4  username=student01  realName=王同学      status=1  role=(无关联)
id=3  username=teacher02  realName=李老师      status=1  role=(无关联)
id=2  username=teacher01  realName=张老师      status=1  role=(无关联)
id=1  username=admin      realName=系统管理员  status=1  role=ADMIN
合计 4 条
```

> ⚠️ **基线很重要。** 你后面的预期值全部基于「开局 4 条用户」。
> 如果你之前已经往库里加过数据、或者跑过一半，基线就不是 4 条了，预期值要按你的实际基线重算。
> 想重置基线：删掉多余用户（逻辑删除后列表里就不显示了），或直接重跑 `sql/schema.sql`（**会清空所有数据**，谨慎）。

### 0-3　在 Apifox 里配好 token

**推荐做法（配一次，后面全用 `{{token}}`）**

1. 打开 Apifox → 右上角环境管理 → 选当前环境 → 新增变量 `token`，值先留空；
2. 建接口 `POST http://localhost:8080/auth/login`，Body 选 JSON：

   ```json
   { "username": "admin", "password": "123456" }
   ```

3. 该接口 → **后置操作 → 提取变量**：变量名 `token`，JSONPath 填 `$.data.token`，作用域选「环境」；
4. 点「发送」，看到 `code=200` 就说明 token 已自动写进环境变量。

之后每个接口的 Headers 里加一行即可：

```
Authorization: Bearer {{token}}
```

**不想配后置操作也可以**：每次登录后手动复制 `data.token`，Headers 里写 `Authorization: Bearer <粘这里>`。

## 三条铁律（违反必错）

| # | 规则 | 说明 |
|---|---|---|
| 1 | **路径不带 `/api`** | 前端的 `/api` 是给 Vite 代理用的，`vite.config.js` 里 `rewrite` 会把它去掉。Apifox 直连 8080 时不写 `/api`，写成 `http://localhost:8080/user/page` |
| 2 | **`Bearer` 后恰好一个空格** | token 不能带引号、换行、`...` 省略号。正常长度是 **172** 个字符 |
| 3 | **id 一律以实测为准，不要假设** | `POST /user` 返回的 `data` 是 `null`，**拿不到新 id**。必须回列表看**第一行**（列表按 id 倒序） |

> 铁律 3 是你原清单最大的坑：原清单里 ⑤ 写 `{"id":4,...}`、⑥ 写 `DELETE /user/4`，
> 但 `id=4` 是 **student01（王同学）**，不是你要操作的新用户。
> 照抄会**把王同学改名成「赵老师2」并把角色改成管理员**，然后**把王同学删了**。
> 本流程统一用占位符 `{新用户id}`，每一步都会提示你从哪读。

## 第 1 轮　登录与鉴权对照

**先做这轮**，因为它同时是「所有接口失败的原因」和「报告里最有价值的异常用例」。

| 步骤 | 操作 | 预期 | 记录 |
|---|---|---|---|
| 1-1 | `POST /auth/login`，body `{"username":"admin","password":"123456"}` | HTTP 200，`code=200`，`data.token` 长度 172，`role="ADMIN"` | ☐ |
| 1-2 | `GET /user/page?pageNum=1&pageSize=10`，**故意不带** `Authorization` | **HTTP 403，响应体完全为空** | ☐ |
| 1-3 | 同上，Header 填 `Authorization: Bearer abc.def.ghi`（伪造） | HTTP 403 | ☐ |
| 1-4 | 同上，Header 填正确 token | HTTP 200，`code=200` | ☐ |

> **1-2 看到的「403 + 空白」不是 bug，是预期行为。**
> `SecurityConfig` 只放行 `/auth/login` 和 `/hello`，其余走 `anyRequest().authenticated()`；
> 而它没配 `AuthenticationEntryPoint`，Spring Security 6 默认用 `Http403ForbiddenEntryPoint`，
> 所以只给状态码、不给响应体。
> **这条一定要截图**，它是报告 6.3「问题一」的证据。

## 出问题时的定位顺序

按这个顺序查，别乱试：

| 现象 | 先查什么 | 结论 |
|---|---|---|
| 所有接口返 403 且响应体空白 | Headers 里有没有 `Authorization` | 缺令牌，见第 1 轮 |
| 加了令牌还是 403 | token 长度是不是 172？`Bearer` 后是不是恰好一个空格？ | 令牌被截断/格式错 |
| 令牌格式没问题还是 403 | 距离上次登录是否超过 24 小时 | 令牌过期（`expire: 86400000`），重新登录 |
| 返回 404 | 路径是不是多了 `/api` | 去掉 `/api` |
| 返回 405 | 方法用错（`PUT` 发成了 `POST` 等） | 对照流程表里的方法 |
| `code=500` 且 message 有中文提示 | 这是**业务异常**，不是服务挂了 | 看 message 内容，如「用户名已存在」 |
| 页面能点通、Apifox 不通 | 页面走了 Vite 代理且自动带 token | 属正常，按本条规则在 Apifox 里补令牌 |
| 什么都对但数据不对 | 看后端控制台 SQL 日志，确认请求是否进了 Controller | SQL 一条没打 = 被过滤器拦了 |

**快速判定工具**：任何时候拿不准是服务端还是客户端问题，跑

```bash
node exam-backend01/scripts/verify-api.mjs
```

它只读、不改数据，跑出 `12 通过 / 0 失败` 就说明服务端完全正常，问题一定在 Apifox 配置。

## 两个可以直接写进报告的额外发现

跑完流程后，这两条是真实验证过的行为，写进报告能加分：

**（1）未认证请求返回 403 且无响应体**

不是 401，也没有 `{code, message}`。原因：`SecurityConfig` 未配置 `AuthenticationEntryPoint`，
Spring Security 6 默认使用 `Http403ForbiddenEntryPoint`。
**改进方向**：配置自定义 entryPoint，返回 `{"code":401,"message":"未登录或登录已过期"}`，
让前端能区分「未登录」和「无权限」并跳转登录页。

**（2）逻辑删除后，同名用户名可以被重新注册**

`save()` 的查重语句是 `selectCount(... eq(username, ...))`，`@TableLogic` 会自动追加 `deleted=0`，
所以已逻辑删除的用户不参与查重。
想验证：把 7-1 删掉的 `teacher04` 再新增一次，会返回 `code=200` 而不是「用户名已存在」。
**这算一个设计缺陷**：同一个用户名会指向两条历史记录，可能造成混淆。
**改进方向**：查重时忽略逻辑删除（自定义 SQL 加 `WITH deleted` 条件），或给 `(username, deleted)` 建联合唯一索引。

> 第（2）条你可以在 7-4 之后顺手试一下，算一条额外用例。如果试了，记得把 total 再核对一遍。
