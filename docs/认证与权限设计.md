# 认证与权限设计

> 第 4 周（上午）· 软件工程综合实践 产出物
> 项目：在线考试系统（exam-backend01 / exam_front）

## 一、认证方案设计说明

### 1.1 Session 与 Token 对比

本项目是前后端分离 + 三端（PC / 小程序 / App），选择 **Token（JWT）方案**。

| 维度 | Session（有状态） | Token（本项目采用） |
|---|---|---|
| 状态 | 有状态：服务器存会话信息 | 无状态：服务器不存，靠令牌自证 |
| 存储位置 | 服务端 Session + 客户端 Cookie | 客户端（localStorage），请求头携带 |
| 多端支持 | 依赖 Cookie，小程序/App 不便 | 三端统一用请求头，天然适合 |
| 扩展性 | 多服务器需共享 Session | 无状态，易水平扩展 |

### 1.2 JWT 原理

JWT 由三段 Base64 编码组成，用 `.` 分隔：`Header.Payload.Signature`

| 段 | 内容 | 作用 |
|---|---|---|
| Header | 算法（如 HS256）、类型（JWT） | 声明签名算法 |
| Payload | 携带的数据（用户名、角色、过期时间） | 存放业务信息（不加密，只编码） |
| Signature | 用密钥对前两段签名 | 防篡改：改任何内容签名就失效 |

> 关键理解：JWT 的签名保证"内容没被改过"，但 Payload 是可解码阅读的，
> **不要把密码等敏感信息放进 JWT**。

### 1.3 登录认证流程

1. 用户提交账号密码
2. 服务端校验账号密码
3. 校验通过 → 签发 JWT（含用户名、角色），返回给客户端
4. 客户端保存 token，之后每次请求在 Authorization 头携带
5. 服务端过滤器验签，合法则放行

## 二、RBAC 权限模型

### 2.1 什么是 RBAC

RBAC（Role-Based Access Control，基于角色的访问控制）用三个概念管理权限：

- 用户（User）：使用系统的人
- 角色（Role）：权限的集合，如"管理员""教师""学生"
- 权限（Permission）：能做什么，如"管理用户""发考试"

关系：用户 ↔ 角色 ↔ 权限。用户与角色是多对多，通过中间表 `sys_user_role` 关联（第 2 周已建）。

### 2.2 三角色权限矩阵

| 功能 | 管理员 | 教师 | 学生 |
|---|---|---|---|
| 用户管理 | ✅ | ❌ | ❌ |
| 角色分配 | ✅ | ❌ | ❌ |
| 题库管理 | ❌ | ✅ | ❌ |
| 组卷 | ❌ | ✅ | ❌ |
| 考试发布 | ❌ | ✅ | ❌ |
| 成绩管理 | ❌ | ✅ | ❌ |
| 在线答题 | ❌ | ❌ | ✅ |
| 查看成绩 | ❌ | ✅ | ✅（仅自己的） |

### 2.3 角色编码与鉴权策略

- 角色编码：`ADMIN` / `TEACHER` / `STUDENT`
- 登录后把角色编码写入 JWT 的 `role` 字段
- 后端据此做**接口级鉴权**，前端据此做**页面/按钮级显示**
